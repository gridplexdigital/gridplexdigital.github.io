HUI Year-Long Implementation Roadmap

Executive Summary

This roadmap outlines a pragmatic 12-month implementation plan for building a domain-agnostic knowledge graph infrastructure with semantic search capabilities. The plan is designed for a 2-person part-time team (~40 hours/week total) and prioritizes real AI/ML capabilities over UI polish.

Key Milestones:

  • Month 3: MVP with basic semantic search and ontology explorer
  • Month 6: Enhanced search and multi-modal content support
  • Month 9: API layer, authentication, and analytics
  • Month 12: Production-ready system with monitoring and documentation

Strategic Approach:

  • Build generic knowledge graph infrastructure (domain-agnostic)
  • Leverage existing hui-prototype (React) and hui-backend (FastAPI)
  • Focus on working AI/ML over polished UI
  • Prioritize low-hanging fruits and incremental value delivery

Phase 1: MVP Foundation (Months 1-3)

Goal

Deliver a working knowledge graph system with semantic search and basic ontology exploration capabilities.

Sprint 1 (Weeks 1-2): Infrastructure Setup

Objectives:

  • Set up cloud infrastructure and development environments
  • Configure databases (Neo4j for graph, Qdrant/Weaviate for vectors)
  • Establish CI/CD pipeline

Deliverables:

  • Cloud infrastructure provisioned (AWS/GCP/Azure)
  • Neo4j graph database deployed
  • Vector database (Qdrant or Weaviate) deployed
  • Redis cache configured
  • Development and staging environments ready
  • GitHub Actions CI/CD pipeline

Technical Decisions:

  • Graph Database: Neo4j (mature, good Python support, Cypher query language)
  • Vector Database: Qdrant (open-source, self-hostable, good performance)
  • Cloud Provider: AWS (comprehensive services, good documentation)
  • Primary LLM: Ollama (self-hosted Llama 3, Mistral, Mixtral for 70-80% of tasks)
  • Secondary LLM: OpenAI (GPT-4 for complex/critical tasks, 20-30% of requests)
  • Embeddings: Sentence-Transformers (free, fast) + OpenAI (high quality when needed)
  • GPU: NVIDIA T4 (dev) → A10G (production)

Estimated Effort: 80 hours (2 weeks × 40 hours)

Sprint 2 (Weeks 3-4): Domain-Agnostic Knowledge Graph Schema

Objectives:

  • Design and implement generic knowledge graph schema
  • Create ontology loading mechanism
  • Build basic entity and relationship models

Deliverables:

  • Generic entity and relationship schema in Neo4j
  • Ontology definition format (JSON/YAML)
  • Ontology loader service
  • Sample ontology for testing (generic concepts)
  • Database migration scripts

Schema Design:

Entity Node:
- id: UUID
- type: string (from ontology)
- name: string
- properties: JSON (flexible, ontology-defined)
- ontology_namespace: string
- created_at: timestamp
- source_document_id: UUID

Relationship Edge:
- id: UUID
- type: string (from ontology)
- source_entity_id: UUID
- target_entity_id: UUID
- properties: JSON
- ontology_namespace: string
- created_at: timestamp

Estimated Effort: 80 hours

Sprint 3 (Weeks 5-6): Data Ingestion Pipeline

Objectives:

  • Build text document ingestion system
  • Implement chunking and embedding generation
  • Create entity extraction logic

Deliverables:

  • Document upload API endpoint
  • Text chunking service (semantic chunking)
  • Embedding generation service (OpenAI API integration)
  • Entity extraction service (NER + ontology matching)
  • Vector storage in Qdrant
  • Entity storage in Neo4j
  • Provenance tracking

Technical Implementation:

  • Use LangChain for document processing and chunking
  • Implement semantic chunking (not fixed-size)
  • Generate embeddings using OpenAI text-embedding-3-large
  • Store embeddings with metadata in Qdrant
  • Extract entities using spaCy + custom ontology matching
  • Create entity nodes and relationships in Neo4j

Estimated Effort: 80 hours

Sprint 4 (Weeks 7-8): Semantic Search with RAG

Objectives:

  • Implement semantic search endpoint
  • Build RAG pipeline for answer generation
  • Add citation tracking

Deliverables:

  • Semantic search API endpoint
  • Vector similarity search in Qdrant
  • RAG pipeline with OpenAI GPT-4
  • Citation extraction and linking
  • Search result ranking
  • Response streaming support

RAG Pipeline:

  1. Convert query to embedding
  2. Retrieve top-k similar chunks from Qdrant
  3. Fetch related entities from Neo4j
  4. Construct context with citations
  5. Generate response with GPT-4
  6. Extract and return citations

Estimated Effort: 80 hours

Budget Scenarios

Conservative Scenario (Low Usage):

  • Small dataset (<100K documents)
  • Limited users (<100 active users)
  • Moderate LLM usage (mix of Ollama + OpenAI)
  • Estimated: ₹20,00,000-25,00,000/year

Moderate Scenario (Medium Usage):

  • Medium dataset (100K-500K documents)
  • Growing user base (100-1000 users)
  • Regular LLM usage (balanced Ollama + OpenAI)
  • Estimated: ₹35,00,000-45,00,000/year

Aggressive Scenario (High Usage):

  • Large dataset (>500K documents)
  • Large user base (>1000 users)
  • Heavy LLM usage (primarily OpenAI for quality)
  • Estimated: ₹55,00,000-80,00,000/year

Cost Optimization Strategies

  1. LLM Costs (largest variable):
    • Use Ollama for routine tasks: Deploy Llama 3, Mistral, or Mixtral models on GPU instances for:
      • Entity extraction and classification
      • Basic question answering
      • Text summarization
      • Embedding generation (using sentence-transformers)
    • Reserve OpenAI for complex tasks: Use GPT-4 only for:
      • Complex reasoning and analysis
      • High-quality content generation
      • Critical user-facing responses
    • Hybrid approach savings: Can reduce OpenAI costs by 60-80%
    • Cache frequent queries and responses
    • Implement query result caching
    • Batch embedding generation
  2. Ollama Infrastructure:
    • GPU Requirements:
      • Development/Testing: 1x NVIDIA T4 (16GB VRAM) - ₹30,000-40,000/month
      • Production: 1x NVIDIA A10G (24GB VRAM) - ₹60,000-80,000/month
      • High Load: 2x NVIDIA A10G or 1x A100 - ₹1,20,000-2,00,000/month
    • Models to deploy:
      • Llama 3 8B (fast, general purpose)
      • Mistral 7B (efficient, good quality)
      • Mixtral 8x7B (high quality, slower)
      • Sentence-transformers for embeddings (free, fast)
    • Cost comparison:
      • OpenAI GPT-4: ₹3,000 per 1M tokens
      • Ollama (self-hosted): ₹0 per token (fixed GPU cost)
      • Break-even: ~20M tokens/month
  3. Database Costs:
    • Self-host Neo4j and Qdrant instead of managed services
    • Optimize queries to reduce compute
    • Implement data archival for old content
    • Use read replicas for scaling reads
  4. Cloud Infrastructure:
    • Use spot instances for non-critical workloads (50-70% savings)
    • Implement auto-scaling to match demand
    • Optimize storage with lifecycle policies
    • Use CDN for static assets
  5. Monitoring:
    • Use open-source tools (Prometheus, Grafana)
    • Implement sampling for high-volume metrics
    • Aggregate logs before storage

Ollama Model Selection Strategy

Primary Models:

  1. Llama 3 8B (Fast, General Purpose)
    • Use for: Entity extraction, classification, basic Q&A
    • Speed: ~50 tokens/second on A10G
    • VRAM: 8GB
    • Quality: Good for most tasks
  2. Mistral 7B (Efficient, Balanced)
    • Use for: Summarization, content generation
    • Speed: ~60 tokens/second on A10G
    • VRAM: 7GB
    • Quality: Excellent efficiency/quality ratio
  3. Mixtral 8x7B (High Quality, Slower)
    • Use for: Complex reasoning, critical responses
    • Speed: ~20 tokens/second on A10G
    • VRAM: 24GB (requires full GPU)
    • Quality: Near GPT-3.5 level
  4. Sentence-Transformers (Embeddings)
    • Use for: Document embeddings, semantic search
    • Speed: Very fast (CPU-based)
    • VRAM: 0GB (runs on CPU)
    • Cost: Free, no API costs

    • Savings: 80% on OpenAI costs

Medium-Term Savings (Months 4-9)

  1. Deploy Ollama for Routine Tasks: Replace 70% of OpenAI calls

    • Savings: 20-30% better GPU utilization

Data Flow

Document Ingestion Flow: 1. User uploads document via API 2. Document is queued for background processing 3. Text is extracted and chunked semantically 4. Chunks are embedded using OpenAI API 5. Embeddings stored in Qdrant with metadata 6. Entities extracted using NER + ontology matching 7. Entities and relationships stored in Neo4j 8. Provenance links created from entities to source

Semantic Search Flow: 1. User submits natural language query 2. Query is embedded using OpenAI API 3. Vector similarity search in Qdrant retrieves top-k chunks 4. Related entities fetched from Neo4j 5. Context constructed with chunks + entities 6. GPT-4 generates response with citations 7. Response returned to user with source links

Ontology Exploration Flow: 1. User requests entity or graph view 2. Cypher query executed against Neo4j 3. Graph data returned with entities and relationships 4. Frontend renders interactive visualization 5. User clicks entity for details 6. Entity properties and connections displayed
